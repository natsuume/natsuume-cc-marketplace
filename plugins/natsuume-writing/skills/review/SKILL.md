# review

outline skill・draft skill を経た（あるいは既存の）原稿を、書き手が推敲する前段として**4 観点でレビューする**フェーズの詳細手順です。常時注入 (SessionStart) が配送する執筆ルール要点 (`rules/core-summary.md`) を前提に、本 skill は対象ファイルを読み取り、severity 付きの指摘一覧をセッション出力として提示するまでの具体的な手順を提供します。

この `SKILL.md` を含む `skills/review/` の 2 階層上を `<plugin-root>` として解決する。通常の Skill 実行では hook 用の `${CLAUDE_PLUGIN_ROOT}` が設定される保証はないため、reference file は実パスから解決する。

以下の「ユーザーに確認」は `AskUserQuestion` を使い、未確定事項を推測で埋めない。

このセッション (メインセッション) 自身がレビューを行います。文体判断を伴う観点 (1・2・4) は subagent へ委任しません。観点 3 (技術的正確さ) に限り、自身の調査に加えて独立した read-only 調査 subagent を併用します。`codex:codex-rescue` agent を使います。

対象は Markdown ファイルのみです (ReVIEW 形式の技術書原稿はスコープ外のため扱いません)。

対象ファイルは**一切変更しません**。指摘に基づく修正は、ユーザーから明示的な指示があってから (この skill のスコープ外として) 行います。

フローは次の 3 段階です。各段階を順番に進めてください。

## 1. 入力の確認

1. **対象ファイルの確認**。ユーザーの指示やここまでの会話から対象ファイルが明らかな場合はそれを使います。不明な場合はユーザーに確認します。
2. **対象ファイルを読みます**。
   - **境界: ファイルが空、または本文 (地の文) が存在しない場合**。レビュー対象が無いことを報告し、以降の観点別レビューを行わずにこの skill を終了します。
3. **TODO 残存の確認**。対象ファイルに `<!-- TODO: 要検証: ... -->` が残っている場合、件数と内容を控えます (指摘一覧の先頭で報告するために使います)。
4. **outline コメントの確認**。ファイル先頭 (タイトル直後) に `<!-- outline: 媒体=... / 記事タイプ=... / 想定読者=... -->` の形式のコメントがあり、項目が揃っているかを確認します。観点 1 (文体ルール準拠) の判定に、どの媒体プロファイルを適用するかを決めるために使います。媒体 = 書籍 のとき記事タイプは省略可であり (outline / draft skill と同じ契約)、省略されていても欠落とはみなしません。
   - **境界: outline コメントが無い、または項目が欠けている場合**。欠けている項目 — 媒体、記事タイプ (媒体 = 書籍 のときは不要)、想定読者 — をユーザーに確認します。ここで確認した内容はレビューの判断材料としてのみ用い、**対象ファイルへの追記は行いません** (outline コメントの追記は draft skill の責務であり、review skill は読み取り専用です)。

## 2. 4 観点レビューの実施

観点ごとに、対象ファイル全体を通して検出を行います。

### 2-1. 文体ルール準拠

`<plugin-root>/rules/writing-rules.md` を読み込みます。共通コア (セクション 0〜9) と、手順 1-4 で確認した媒体・記事タイプに対応するプロファイル差分 (書籍 / ブログ、企業ブログ・個人ブログのさらなる差分) を適用し、文末表現・語彙・言い回し・表記・文のリズム・構成の型からの逸脱を検出します。

### 2-2. 構成・論理展開

outline コメント・見出し構成と実際の本文との乖離、説明順序の飛躍、内容の重複・欠落を検出します。

### 2-3. 技術的正確さ

1. 原稿中の技術的主張 (バージョン番号・API 仕様・動作・数値など、事実として書かれている記述) を列挙します。
2. 列挙した主張について、自身で調査します。バージョン番号・API 仕様・リリース日など執筆時点より新しくなりうる主張や、学習知識だけでは確度が不足する主張は、WebSearch で公式ドキュメント等の一次情報を確認します (執筆ルールの通底原則「検証していないことを検証したかのように書かない」を、レビュー自身の指摘にも適用するためです)。
3. 上記と併用して、独立した read-only 調査 subagent に調査を委任します。`codex:codex-rescue` agent を起動します。委任指示には次を含めます。
   - 対象ファイルの絶対パス
   - 検証してほしい主張の一覧 (手順 1 で列挙したもの)
   - 読み取り専用の調査であり、対象ファイルを含めて一切のファイルを修正させない旨
   - 修正・実装作業はさせず、事実確認の結果のみを報告させる旨
4. メインセッションの調査結果と独立調査 subagent の findings を主張ごとに突き合わせ、一致・相違を整理します。
   - **境界: codex plugin が未導入、または委任が実行失敗した場合**。メインセッションの調査のみでこの観点を実施し、独立調査を併用できなかった旨を指摘一覧に明記します (エラーで停止せず、他の観点の実施を継続します)。

### 2-4. 誤字脱字・表記ゆれ

1. プロジェクトに textlint / prh の設定ファイル (`.textlintrc*` / `prh.yml` 等) があるか確認します。あり、かつ実行可能な場合は実行し、結果を指摘一覧に取り込みます。
2. 執筆ルールの表記基準 (ひらがなに開く語・カタカナ語の長音符号・算用数字など、`writing-rules.md` セクション 5) は、textlint の有無に関わらず**常に自身でチェックします**。
   - **境界: textlint / prh が未設定、または実行に失敗した場合**。自身のチェックのみでこの観点を実施し、その旨を指摘一覧に明記します (エラーで停止せず、他の観点の実施を継続します)。

## 3. 指摘一覧の提示

セッション出力として、次の形式でまとめます (ファイルへの書き込みは行いません)。

1. **先頭に TODO 残存報告**。手順 1-3 で控えた残存 TODO の件数と内容を列挙します (残存が無い場合はその旨を記載します)。
2. **観点ごとに見出しを立て、指摘を列挙します**。指摘 1 件につき次を記載します。
   - severity (`high` / `medium` / `low`)。判定基準: high = 技術的な誤りや読者を誤導する記述 (事実誤り・動かない手順など)、medium = 執筆ルールや構成からの明確な逸脱で読み味・記事の信頼性を損なうもの、low = 表記の揺れ・語彙の好みなど軽微なもの
   - confidence (`high` / `medium` / `low`)。判定基準: high = ルールの明文や公式情報など確実な根拠がある、medium = 状況証拠にもとづく、low = 疑いの段階であり書き手側での確認が必要
   - 該当箇所 (引用または行番号)
   - 指摘内容
   - 根拠
3. **観点 3 (技術的正確さ) は、メインセッションと独立調査 subagent の findings の一致・相違が分かる形で報告します** (主張ごとに両者の結論を並べ、一致した主張・相違した主張・どちらか一方でしか検出できなかった主張を区別します)。

指摘は**全件報告します**。severity による自己フィルタは行いません (重要度に基づく選別は書き手が行います)。この段階でも対象ファイルは変更しません。
