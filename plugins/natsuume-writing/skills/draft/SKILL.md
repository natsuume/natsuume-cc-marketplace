# draft

outline skill (`/natsuume-writing:outline`) が書き込んだインファイルスケルトン (見出し + HTML コメント) から、執筆ルール準拠のたたき台を**一括生成**するフェーズの詳細手順です。常時注入 (SessionStart) が配送する執筆ルール要点 (`rules/core-summary.md`) を前提に、本 skill はスケルトンの本文化と、未検証事項の TODO 明示までの具体的な手順を提供します。

対象は Markdown ファイルのみです (ReVIEW 形式の技術書原稿はスコープ外のため扱いません)。

執筆そのものは、このセッション (メインセッション) 自身が行います。文体判断を伴う作業のため subagent へ委任しないでください。

フローは次の 4 段階です。各段階を順番に進めてください。

## 1. 入力の確認と前提解決

1. **対象ファイルの確認**。ユーザーの指示やここまでの会話から対象ファイルが明らかな場合はそれを使います。不明な場合はユーザーに確認します。
2. **対象ファイルを読み**、見出し構造と各セクションの状態 (地の文があるか、HTML コメントのみか、空か) を把握します。
3. **スケルトンの確認 (最初に判定する)**。セクション見出しが 1 つも無い場合は、outline コメントの有無に依らずスケルトン不在と判定します。対象ファイルに構成がまだ無いということなので、`/natsuume-writing:outline` の実行を促し、何も書き込まずにこの skill を終了します。構成を勝手に決めて書き始めないでください。
4. **outline コメントの確認 (見出しがある場合のみ)**。ファイル先頭 (タイトル直後) に `<!-- outline: 媒体=... / 記事タイプ=... / 想定読者=... -->` の形式のコメントがあり、項目が揃っているかを確認します。

   - **境界: outline コメントが無い、または項目が欠けている場合**。欠けている項目 — 媒体 (書籍 / 企業ブログ / 個人ブログ)、記事タイプ (技術解説 / 検証レポート / 体験レポート。媒体 = 書籍 のときは省略可)、想定読者 — を `AskUserQuestion` で確認します。ここまでの会話から自明な項目は質問を省略してよいですが、ファイルに追記する時点では各項目が確定していることが条件です (未確定の項目を空欄や仮の値で書き込まないでください)。確定した内容は、生成を始める**前に**ファイル先頭の outline コメントとして追記 (既存コメントがある場合は欠落項目を補完) してください。ここで揃えておくことで、次回以降の draft 実行や review skill が同じ質問を繰り返さずに済みます。

## 2. 執筆ルールの読み込み

`${CLAUDE_PLUGIN_ROOT}/rules/writing-rules.md` を読み込みます。以下を適用します。

- 共通コア (セクション 0〜9): 通底原則・人称・文末表現・語彙・表記・文のリズム・構成の型・コード/図表との絡め方・誠実性の刻印
- outline コメントで確定した媒体・記事タイプに対応するプロファイル差分 (書籍プロファイル / ブログプロファイル、企業ブログ/個人ブログのさらなる差分)
- **セクション 10 (たたき台生成時の特則)**: 本 skill が生成するたたき台自体に適用される規則です。次のステップで具体的に使います。

## 3. 一括生成

対象ファイルのスケルトンをセクションごとに逐次確認しながら書くのではなく、**一括で**本文化します。

1. 各セクションの HTML コメント (書くべき内容・意図・入れる予定の要素の指示) を読み取り、そのセクションの地の文を生成します。本文化したセクションでは、生成の元になった HTML コメント自体は削除します。
2. **境界: 既存本文があるセクション (すでに地の文が書かれているセクション) は一切変更しません**。コメント付き (未執筆) のセクション、または空のセクションのみを本文化の対象とします。
3. **境界: 対象ファイルのすべてのセクションにすでに本文がある場合**。本文化すべき対象が無いということなので、その旨をユーザーに報告し、ファイルには何も書き込まずにこの skill を終了します。
4. 本文化にあたっては、`writing-rules.md` セクション 10 の特則に従い、**未検証の事項を事実として書きません**。該当するのは次のような内容です。
   - 動作確認の結果・計測値
   - 体験談
   - 他章・他記事への参照
   - 具体的な日付やバージョン番号

   これらが必要な箇所は、`<!-- TODO: 要検証: 何を確認すべきか -->` という形式の HTML コメントと、＜プレースホルダー＞ (例: ＜実行結果を記載＞、＜検証したバージョンを記載＞) をセットで地の文に残し、断定文で埋めないでください。「筆者が実際に試した限りでは〜」のような検証帰属文は、書き手が実際に検証したあとで完成させる前提の骨組みとして、TODO コメントとプレースホルダーを伴う形のまま残します。

## 4. 生成後の報告

生成が完了したら、対象ファイルに残した TODO (要検証事項) コメントの一覧を、セクションごとにセッション出力へまとめて提示します。書き手 (ユーザー) が検証すべき事項を一目で把握できるようにするためです。

## 5. 制約

- 対象は Markdown ファイルのみです。ReVIEW 形式などはスコープ外です。
- 執筆はこのセッション自身が行います。文体判断を伴う作業のため subagent へ委任しないでください。
- 既存の地の文 (すでに書かれている本文) の変更・削除は行いません。手を入れるのは、コメント付き (未執筆) または空のセクションに限ります。
