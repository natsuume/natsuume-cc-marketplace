# natsuume 執筆ルール (v3 検収済み確定版)

## 0. 適用範囲と優先順位

このルールは、natsuume 名義で公開する日本語の技術文書 (テックブログ・技術書) の**地の文**に適用する。コードブロック・コマンド例・引用文には適用しない。

- 構成: 「共通コア」(全媒体) + 「媒体プロファイル」(書籍 / ブログ) の 2 層。競合したらプロファイルが優先
- このルールに無い判断が必要になったら、セクション 1 の通底原則から最も近い規則を導出して適用する。列挙されていないから自由、とは解釈しない

## 1. 通底原則 (迷ったらここから導出する)

1. **断定度は情報源に比例させる**。公式ドキュメント・確認済みの仕様は断定し、自分で検証した事実は「筆者が実際に試した限りでは」と帰属を明示し、未検証の推測は婉曲表現に落とす。検証していないことを検証したかのように書かない
2. **読者と並走する**。上から教える口調ではなく、同じ実践者として情報を共有する距離感を保つ。読者が抱きそうな疑問は先回りして代弁し、その場で答える
3. **冷静・抑制**。感嘆・煽り・過度な形容を使わない。淡々と事実と根拠を積む
4. **鮮度と限界を明示する**。執筆時点・バージョン・条件を明記し、情報が古くなる可能性と自分の記述の限界を隠さない

## 2. 人称と読者への距離

- 一人称は「筆者」。ただし**検証・私見の帰属を明示するときだけ**登場させ、単なる主語としては使わない (通常の文は主語を省略する)。「私」は使わない
  - 例: 「筆者の手元で試した限りでは、〜に影響はありませんでした」「筆者個人としては〜することが多いです」
- 二人称 (「あなた」「皆さん」) で読者に呼びかけない。読者への働きかけは「〜してください」「〜したい方は」「〜してみましょう」の形に限る
- 理由: 客観記述を基調にしつつ、経験・好み・裁量が入る箇所だけ「筆者」で明示的に切り出すことで、事実と私見の境界を読者に伝える

## 3. 文末表現

- **です・ます調のみ**。だ・である調を混ぜない。地の文での体言止めは使わない (見出し・表内は可)
- **「！」は使わない。「？」もほぼ使わない**。例外は自問自答の導入 (「では、〜のでしょうか。」と問い、直後の文で自答する) のみ
- 断定度の使い分け (通底原則 1 の具体化):
  - 仕様・事実: 「〜です」「〜します」と断定
  - 推奨・提案: 「〜がよいでしょう」「〜しましょう」「〜しておくのが安全です」
  - 技術的推測・一般論: 「〜と考えられます」「〜と思われます」「〜可能性があります」
  - 筆者の運用・好みの表明: 「〜と思います」「筆者は〜することが多いです」を許容
- 読者の心理を先回りする定型: 「〜と疑問を覚えた方もいるかもしれません」「違和感を覚えた方もいるかもしれません」→ 直後に答える
- ヘッジの常用形: 「〜ことが多いです」「〜場合があります」。断定した直後に「〜と言ってよいと思います」と一段緩める形も可
- **同一の文末表現を近接させない**。「でしょう」を含む文を 2 文連続で置かない。「と思います」は 1 段落に 1 回まで。単調になったら、断定文・名詞述語文 (「〜が〜です」)・動詞文を混ぜてリズムを変える
- **情報を持たない内心の発露を書かない**。「正直、少し反省しました」のような、事実にも判断にも寄与しない感情・心情の表明で文を埋めない。感情に触れる場合は、具体的な出来事・数字とセットにする

## 4. 語彙・言い回し

- 頻用してよい接続詞・副詞: また / なお / ただし / 一方で / たとえば / とはいえ / そのため / したがって / 基本的に(は) / 具体的には / 言い換えると
- シグネチャ表現 (この書き手らしさの核。適所で使う):
  - 「**あくまで**〜」— 機能や主張を過大評価させないための限定・予防線
  - 「**実際、**〜」— 一般論を述べた直後に、具体例・実体験へ橋渡しする
  - 「**一言で言うと**〜」— 新しい概念の説明を、短い要約から始める
  - 「もちろん A ですが、B」— 予想される反論を先に受け止めてから本題に入る譲歩構文
  - 「〜という点です」「〜という観点で」— 切り口を名詞化して提示してから説明に入る
- **シグネチャ表現の密度制御**: 1 セクションあたり 1〜2 個まで。1 つの記事・章にすべての種類を登場させようとしない。文脈が自然に要求するときだけ使い、使わないセクションがあってよい。理由: 実際のコーパスでの出現密度は数千字に 1 回程度であり、詰め込むと途端に機械的な文章になる
- **定型句は文言を変形させない**: 「順番に見ていきましょう」を「順番に見ていきたいと思います」にしない。定型は上記・セクション 7 に示した文言のまま使う
- **演出的なレトリックを使わない**: 解決策を劇的に登場させる型 (「そこで役立つのが〜です」「この問題に対して有効なのが〜です」「ここで登場するのが〜です」) を使わない。ツール・手法の紹介は「〜するためのツールとして〇〇があります」「この問題に対しては、〇〇を利用することで〜できます」と平易に接続する
- **コーパスにない締め・決め台詞を使わない**: 「〜が欠かせません」「〜だと言えます」「〜と言えるでしょう」「〜することが大切です」のような一般論で段落・記事を締めない。締めは事実の要約、次の話題への接続、または未検証事項の率直な開示 (セクション 9) で行う
- 比喩を自作しない。使う場合は出典付きの引用にする (「『MCP とは USB-C ポートのようなものだ』と述べられています」)
- 理由: 断定を避ける慎重さと実証主義がこの書き手の核であり、自作比喩は「検証できない主張」に分類されるため

## 5. 表記 (商業版基準)

- ひらがなに開く: こと / できる / ため / ない / よい / すべて / さまざま / わかる / いただく (「事」「出来る」「為」「無い」「良い」「全て」「様々」と書かない)
- カタカナ語の長音符号は省略しない: サーバー / ユーザー / リポジトリー / ライブラリー / ディレクトリー / エントリー
- 数字は算用数字 (3 つ、2 種類)。漢数字は使わない。英数字は半角
- 括弧: 地の文の補足・言い換えは全角（）。「」は用語の初出強調・UI 文言・引用に使う
- 「※」は使わない。注記・補足は「なお、」「ただし、」で地の文に統合する
- 略称の導入: 「Model Context Protocol（以下、MCP）」の形式で初出時に定義する
- 初出の専門用語は英語併記: 「大規模言語モデル（Large Language Model、以下 LLM）」「Attention（アテンション）」
- 出典 URL は本文に直接書かず、脚注に「タイトル：URL」形式で置く

## 6. 文のリズム

- 長文と短文の緩急をつける。理由節・条件節を読点でつないだ長文 (「〜たり、〜たり、〜たりすることがあります」は 3 連まで可) で構造を積み上げ、直後に短文で締める
  - 例: 長い説明のあとに「順番に見ていきましょう。」
- 読点は主題の提示後 (「〜については、」「〜という点で、」) と節の境界に打つ
- 「なぜ」の説明は結果から離さない。現象を提示した直後に「これは〜のためです」「〜という仕組みによるものです」と近接させる
- **同じ趣旨を繰り返さない**: 1 つの主張は 1 回だけ述べる。文を足すのは、根拠・具体例・例外・手順など新しい情報を加えるときのみ。前の文の内容を別の言い回しで反復しない (「言い換えると〜」による言い換えは、専門用語を平易にする場合に限る)

## 7. 構成・列挙の型

- **数を予告してから列挙する**: 「大きくふたつあります」「以下の 3 つの観点から〜」→ 箇条書き → **直後に地の文で回収する** (箇条書きを言いっぱなしにしない)
- 箇条書きの導入は「〜は以下のとおりです。」「以下のような〜」。文末コロン (「〜です：」) は使わない
- **導入定型を二重に使わない**: 「大きく 3 つあります。具体的には以下のとおりです。」のように数の予告と「以下のとおりです」を重ねない。どちらか一方で箇条書きに入る
- 番号付きリストは手順・選択肢のみ。並列的な項目列挙は「-」を使う
- 箇条書き項目の文体を揃える (すべて文で終えるか、すべて名詞句か。「〜という点です」と「〜できます」を混在させない)
- 全体像の列挙 → 「順番に見ていきましょう」→ 個別詳細、の二段階構成
- 比較・一覧情報は積極的に表へ落とす。**3 つ以上の並列要素 (機能・選択肢・比較軸・手順) を地の文で流さない**。箇条書き・表・番号付きリストのいずれかに構造化する。地の文が 3 段落以上構造化要素なしに続いたら、列挙・比較を見落としていないか確認する
- 章・節の冒頭は「前章では〜について解説しました。本章では〜について解説します」の型で、前の要約と今回のスコープ宣言から始める
- 見出しは体言止め (名詞句)。定義セクションは「〜とは」形式も可
- 段落は 3〜6 文で 1 トピック

## 8. コード・図表との絡め方

- コード・図の前に必ず予告文: 「以下のように記述することで、〜できます」「〜は以下のようになります」
- コード・図の直後に必ず回収文: 「このように、〜が確認できます」。貼りっぱなしにしない。ただし回収文には新情報 (この設定で何が起きるか・どこに注意するか・次に何を確認するか) を含める。コードの内容を日本語でなぞるだけの文 (「これは〜を読み込んでいることを示しています」) は書かない
- 別ファイルの内容を 1 つのコードブロックに同居させない。ファイルごとにコードブロックを分け、それぞれにファイル名をコメントまたは直前の地の文で示す
- 実行結果は検証済みの事実として書く: 「〜が確認できました」
- 数値・計測結果は「提示 → 定性ラベル（良好/中等度など）→ 文脈での意味づけ」の 3 段で解釈を添える

## 9. 誠実性の刻印

- 「執筆時点では」を恐れず繰り返す。挙動の記述にはバージョン・日付を添える (「本セクション執筆時点のバージョン (Claude Code v2.0.59) で確認した挙動です」)
- 独自解釈・推測を述べる直前に断り書きを入れる: 「なお、本セクションの内容には筆者独自の解釈が一部含まれています」
- LLM を扱う場合は確率的性質への言及を挟む: 「Claude Code（LLM）は確率的なモデルなので、本書と同じ動作をするとは限りません」
- コスト・件数など具体的な数値は伏せずに開示する (実証主義)
- できていないこと・試せていないことは率直に書く: 「筆者は〜を本格的に試すことはできていません」

## 10. たたき台生成時の特則 (AI がたたき台を書くとき)

- **未検証の事項を事実として書かない**。動作確認の結果・計測値・体験談・他章や他記事への参照・具体的な日付やバージョン番号は、AI が生成した時点では未検証である
- 該当箇所は `<!-- TODO: 要検証: 何を確認すべきか -->` コメント + プレースホルダーで明示する。「筆者が試した限りでは〜」等の検証帰属文は、書き手の実検証後に完成させる前提の骨組みとして残す
- 理由: 通底原則 1 (検証していないことを検証したかのように書かない) は、生成するたたき台自体にも適用される。捏造された体験談・検証記述は、この書き手の文体の核である実証主義と正面から矛盾する

## 書籍プロファイル (共通コアへの差分)

- 巻頭に「免責事項」セクションを置く定型 (対象バージョン範囲・正確性への留保・商標表記)
- 章末に明示的な「まとめ」節は置かず、最後の話題の延長で緩やかに閉じる。仕様一覧的な「〜のまとめ」は表形式の小節として本文中に置く
- コラムの用途を固定する: 本筋から外れる余談・補足と、執筆後に生じた仕様変更の追記 (パッチ) に限定
- 見落とすと危険な警告は**太字の一文**で打ち出し、直後に推奨行動を続ける: 「**誤って削除した場合でも復元できません。**したがって、バージョン管理は別途 git などで行うようにしましょう」
- 他章への相互参照 (「詳しくは第 N 章で解説します」「前述のとおり」) を積極的に張る

## ブログプロファイル (共通コアへの差分)

- **記事タイプで導入を使い分ける** (エッセイ的な個人体験から入る導入は体験レポート型に限る):
  - 技術解説・ハウツー: 課題・背景 → 本記事で扱う範囲の宣言、の順で入る。個人の体験談から始めない
  - 検証・実験レポート: 冒頭にサマリー (結論・結果の箇条書き 3 点程度) → 背景・目的 → 方法 → 結果 → 考察の構成
  - 体験レポート (イベント参加記等): 状況・イベントの事実から直接入る。この型に限り個人的な語りを導入に使ってよい
- 図表は番号キャプションではなく会話的に参照する (「下図のようになります」「上記のとおり」)
- 結びは「〜していきたいと思います」「〜していきたいところです」の前向きな意志表現で締める

### 企業ブログのとき

- 冒頭定型: 「こんにちは。〇〇の△△です。」+ 近況一言 + 「今回は〜について紹介します。」
- 感情語・口語ヘッジは使わない。「において」等のやや硬い語彙を許容
- 冒頭免責 (任意): 「※こちらの記事は作成日時点の内容に基づいています」

### 個人ブログのとき

- 挨拶 (「こんにちは。〜です。」) を書かない。導入は上記の記事タイプ別パターンに従う
- 一人称に「自分」を使ってよい。「正直」「個人的には」「ちなみに」などの口語ヘッジ、感情表現 (「すごく嬉しかったです」)、(笑) を許容
- ただし感情表現は実際の出来事・具体的な事実に付随する場合のみ。内容に寄与しない内心の発露だけの文は書かない (共通コア 3 の規則がここでも優先される)
- 売上・費用などの数字も率直に開示する
