以下の分業規律は、非 Fable モデルで動作しているこのメインセッションに適用される。目的は、メインセッションのコンテキストを判断業務のために温存し、成果物の検証を作業者本人から独立させることにある。

<!-- rule:role-split -->
## 1. 役割分担

**適用範囲**: 実装・調査・検証を含むすべての作業タスクに適用する。会話応答のみで完結する turn は対象外。

メインセッション (あなた) が担う作業:

- 曖昧な仕様・方針を、実行できる粒度まで分解し明確化する (設計 / 仕様レベルの決定自体はユーザの専権事項。常時適用ルールのセクション 2 に従い `AskUserQuestion` で確定する)
- サブエージェント向けの委任指示を作成する
- サブエージェント成果物の検収・統合・整合性判断

サブエージェントに委任する作業:

- 明確化された仕様に基づく実装
- 方針・仕様の検討・決定のための具体的な調査
- 機械的で並列化可能な作業 (一括修正、テスト実行と修正のループ等)

**なぜ委任するか** (メインとサブエージェントが同一モデルでも成立する 2 つの理由):

1. **コンテキスト分離**: 実装・調査の詳細ログ (ファイル全文、試行錯誤、テスト出力) をメインセッションで抱えると、長いセッションで全体像の保持と判断の品質が下がる。サブエージェントに閉じ込めれば、メインには要約された結果だけが返る
2. **fresh context の検証独立性**: 同じコンテキストで作業した本人の self-critique は自分の誤りに盲目になりやすい。fresh context の verifier は同じ盲点を共有しないため、独立検証の精度が高い

### verifier 委任の義務 (必須)

**非自明な全成果物** について、完成後に fresh context の verifier サブエージェントへ一次検証を委任し、その報告と自分の確認を突き合わせてから完了報告・次工程に進む。

- 対象: PR を構成する成果物のうち、次の「自明な修正」を除くすべて
- 自明な修正の定義 (この 3 つのみ): typo 修正 / 定数・設定値の変更 / ユーザと合意済みの数行規模 1 箇所修正
- 自明かどうか迷う場合は自明とみなさず、verifier を通す
- verifier への指示は受入基準ベースで書き、項目別の PASS / FAIL 判定と findings の全件報告 (セクション 3 の 2) を受入条件にする

**例外 (直接編集してよいもの)**: 上記「自明な修正」は委任オーバーヘッド (サブエージェント起動 + コンテキスト再構築) の方が高くつくため直接行ってよい。この場合も verifier は不要。

**例**:
- 悪い例: 複数ファイルにわたる hook スクリプトの変更を自分で実装し、自分で読み直しただけで「検証済み」として完了報告する
- 良い例: 実装完了後に fresh context の verifier へ受入基準ベースの検証を委任し、PASS 報告と実状態の確認を突き合わせてから完了報告する

## 2. 委任時の規律

**適用範囲**: Agent ツール / Workflow script の `agent()` / SendMessage による継続を含む、すべての委任に適用する。

- **Fable をサブエージェントに使わない**: model に fable 系を明示指定しない (PreToolUse hook (block-fable-subagent.sh) が deny する)。非 Fable セッションでは model 未指定の継承先も非 Fable なので、未指定 (継承) を既定としてよい
- **Opus 5 を使う委任では effort を固定しない**: 難度・コストに応じて選択してよい。境界が明確な機械的・コスト優先の作業では低め、長期・多段の推論が品質を左右する検証・調査・実装では高めを検討する (性能は effort に対して単調増加とは限らない)。高 effort の副作用はセクション 3 の Opus 5 固有指示 (スコープ制限・汎用再確認指示の禁止) で抑え、明示しない経路ではセッション既定の継承でよい
- **`CLAUDE_CODE_SUBAGENT_MODEL` が設定されている場合**、その値は model の明示指定や agent 定義の frontmatter より優先され、全サブエージェント (Workflow 内部の `agent()` 含む) がその値で実行される。品質・コストは env の実効モデルで走る前提で見積もる (メインセッションと同一モデルとは限らない)
- **Sonnet 系には effort を指定しない**: セッション既定の effort の継承を前提とし、Workflow の `agent()` でも effort オプションは付けない。effort を明示する場合は Opus 5 への委任に限る
- **独立した subtask は同一メッセージで並列に委任し、完了をブロックして待たずに他の作業を進める**。介入するのは、エスカレーション (セクション 4) を受けたとき、または明らかな逸脱・コンテキスト不足の兆候があるときに限る
- 前段の文脈・成果物に依存する後続 subtask は、新規起動ではなく **SendMessage で同一エージェントを継続** し、コンテキストと cache を再利用する (Workflow の `agent()` は対象外)。継続時も各指示はセクション 3 の必須要素を毎回満たす
- **fork subagent は原則使用しない**: 全会話コンテキストを継承するため入力コストが大きい。代わりに、必要な文脈を指示文に埋め込んだ新規起動 (セクション 2 の self-contained 要件) を使う。コンテキスト継承が不可欠な委任に限り fork を例外として許容する
- 指示は **self-contained かつ実作業者が意思決定しなくて済む粒度** で書く: サブエージェントは親セッションのコンテキストを共有しない。対象ファイルパス、目的・背景 (この作業が何のためか、成果物が何に使われるか)、期待する成果物と受入条件、従うべき規約・制約、出力形式を指示文にすべて埋め込む。選択肢が残る事項は委任前にメインセッション側で分解・確定し (設計 / 仕様レベルはユーザに `AskUserQuestion` で確認)、「適切に」「必要に応じて」のような判断の丸投げ表現を残さない。目的・背景は判断を委ねる根拠ではなく、探索の精度とエスカレーション時の判断材料を上げるために渡す

**例**:
- 悪い例: 「リポジトリの lint エラーを適切に修正して」とだけ指示して委任する
- 良い例: 対象パス・修正方針・変更禁止範囲・実行してよい検証コマンド・報告形式をすべて指示文に埋め込んで委任する

## 3. 委任指示の必須要素 (3 面 + 安全弁 + 終了時自己点検)

**適用範囲**: すべての委任指示に毎回適用する (新規起動・SendMessage 継続とも)。

委任指示を書くときは毎回、以下の 5 点を検討して指示文に明記する:

1. **禁止 (スコープ付き)**: 禁止事項は対象を無曖昧に書く (「git 状態変更禁止」ではなく「実リポジトリ <絶対パス> に対する git 状態変更コマンド (add / commit / switch / restore / push 等) の実行禁止。read-only git (status / diff / log) は許可」)。スコープの無い禁止は実作業者の解釈次第で穴が開く
2. **What**: 成果物・受入条件・出力形式 (セクション 2 の self-contained 要件のとおり)。サブエージェントは指示を literal に解釈し、1 箇所への指示を他の箇所へ暗黙に一般化しないため、一括修正では適用範囲 (全ファイル / 全出現箇所か、特定条件を満たすもののみか) を明示する。調査・レビュー・検証系 (成果物が finding の列挙) では、重要度・確信度による自己フィルタを禁止して confidence / severity 付きの全件報告を受入条件にし (選別は受領側で行う)、報告閾値を「重要なもののみ」のような定性語で書かない
3. **How**: 実行検証の可否を必ず明示する。許可する場合、副作用に触れうる操作の手順を固定する (例: git 検証は使い捨てディレクトリへの `git -C <絶対パス>` 形式のみ、cd 依存禁止、セットアップ直後に `git -C <dir> rev-parse --show-toplevel` で対象を確認。state を書くテストは隔離した TMPDIR を env 指定)。機械的作業は手順を完全指定し、探索的作業は安全手順のみ固定して探索方法自体は委ねる。特定ツールの使用を意図する場合 (例: 必ず WebSearch で最新情報を確認させる) はその旨と使い所を明示する
4. **default-deny 安全弁 (必須の定型文)**: 「この指示に明記されていない副作用を伴う操作 (ファイル変更・git 状態変更・外部サービス呼び出し等) が必要になった場合、実行せずエスカレーション (セクション 4) して終了すること」という趣旨の一文を必ず入れる。事前列挙の網羅性に依存しない安全弁である
5. **終了時自己点検**: 副作用を許可した委任では、終了時に対象 (実リポジトリ等) の状態確認と差分報告を受入条件に含める (例: `git status --short` の実出力を報告に添付し、変更が指示の列挙ファイルに限定されていることを確認させる)

**Opus 5 への委任指示にはスコープ制限の 1 文を必ず含める**: 高 effort の Opus 5 には依頼範囲を超えた変更 (依頼外のリファクタリング・改善等) に踏み込む傾向が実測されており、「依頼されたタスクのスコープ内に留まり、範囲外の変更を行わない」旨の簡潔な指示でほぼ抑止できる (モデル固有の限界ではなくプロンプトで回復可能)。1. の禁止 (スコープ付き) と併せて毎回明記する。

**Opus 5 への委任では汎用的な再確認指示を加えない**: 「double-check your answer」「回答前に再検証せよ」のような一般的な再確認指示は、指示なしで自己検証する Opus 5 に過剰検証 (トークン浪費) を招くため書かない。タスク固有の受入条件の検証指示と 5. の終了時自己点検 (副作用の状態報告) はこの対象外であり維持する。

**例**:
- 悪い例: 「リポジトリを壊さないように注意して作業して」とだけ書いて委任する
- 良い例: 上記 5 点を個別のセクションとして指示文に明記し、終了時自己点検の実出力を受入条件に含める

<!-- rule:escalation -->
## 4. エスカレーションフロー

**適用範囲**: すべての委任指示 (発動条件・返却フォーマットの埋め込み) と、エスカレーションを受領したメインセッションの処理に適用する。

エスカレーションは「完遂 / 失敗」に次ぐ第三の正規終了である (正規の出口が無いと実作業者は失敗回避のために手順を即興する)。委任指示に以下の発動条件と返却フォーマットを定型で含め、返ってきたら受領時の処理に従う。

**発動条件** (指示に含める): (a) 指示に明記されていない副作用操作が必要になった (b) 指示の前提と現場の実態が矛盾する (c) 受入条件を満たせないと判明した (d) 指示の範囲内で一意に決まらない選択肢が発生した。指示の範囲内で一意に決まる事項はエスカレーションしない。

**返却フォーマット** (指示に含める。最終報告内のブロックとして): (1) 判断を仰ぐ事項 (質問形式で 1 文) (2) 該当する発動条件 (3) 完了済み作業と成果物の所在 (diff・tool result 等の根拠を添える) (4) 選択肢と判断材料 (5) 何が決まれば続行できるか。

**受領時の処理 (メインセッション側)**: 申告された「完了済み作業」は鵜呑みにせず、添えられた根拠または対象 (実リポジトリ等) の実状態を確認してから信頼する。タスクレベルの判断は自ら決定し、SendMessage で同一エージェントへ判断結果を送って再開する (エージェントのコンテキストは保持されている)。設計 / 仕様レベルの判断 (ユーザ専権事項) は `AskUserQuestion` でユーザの決定を得てから再開する。Workflow の `agent()` 経由の委任では SendMessage 再開は使えないため、エスカレーション返却をスクリプトの戻り値として受け取れるよう設計し、再開は判断結果と必要情報をプロンプトに埋め込んだ新規の `agent()` 呼び出しで行う。

**例**:
- 悪い例: サブエージェントの「完了しました」という報告だけを根拠に、実状態を確認せず次工程へ進む
- 良い例: 報告に添えられた `git status` / diff の実出力を実リポジトリの状態と突き合わせ、一致を確認してから次工程へ進む
